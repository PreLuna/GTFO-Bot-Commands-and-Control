| --- | --- | --- |

最新日志CPU准备16.69／5.32ms，首次观察提交41.83ms，接管提交12.58／6.37ms，恢复观察6.41／7.01ms，释放9.78／1.36ms；只作为本场景阶段CPU墙钟证据，不当作GPU帧时、全地图或全部MOD组合保证。沿用的离线证据是机器人34组、第三人称18组、武器6组，配置迁移实际Load9项、运行器303项、实际BepInEx范围34项与混合安装5条硬依赖。本次补验收文档没有改实现或重跑构建，代码输入与保留构建锁逐项核对一致。

## 当前手电常亮机制

### 范围与配置

MicroMaster的灯光服务独立于接管会话。默认`[接管手电] 原生手电常亮=true`、`[人机手电] 模式=AllBots`：房主处于有效关卡、楼层与人机身份有效、对象尚未销毁／离队时，管理所有人机已有的原生装备灯或头盔灯。是否按T、是否打开Q、AI状态、休眠敌人和前方真人不再决定是否允许关灯。

倒地但对象仍存在时，灯策略继续；这没有放宽接管本身的存活等安全要求。`ControlledOnly`仅接管期间管理；`AI`或关闭总开关交还原版。强制模式中的F只报告状态，不切换关闭。

离开关卡、对象销毁／离队、配置关闭、房主或楼层身份失效及卸载时撤销管理。恢复原开关必须能通过自己的保护；失去房主后不继续向远端广播恢复请求。真人灯不归此服务管理。

### 三个写入边界

| 原生入口 | 0.5.14处理 |
| --- | --- |
| `PlayerSync.WantsToSetFlashlightEnabled(false, broadcastOnly)` | 拒绝受管人机的false请求；**不把每帧false改成每帧true广播** |
| `PlayerInventoryBase.ReceiveSetFlashlightStatus(false, playSound)` | 阻止旧同步／本地接收状态清掉开灯意图 |
| `PlayerInventoryBase.SetFlashlightEnabled(false, allowHelmetLight, playSound)` | 阻止直接关闭当前受管灯；只为明确的装备解绑作用域和主动归还放行 |

保护不依赖参数就绪或渲染就绪。参数非法时仍保留有限值保护，不通过强开无效灯、直接更新GPU数据解决。

装备交接中，`UnWieldFlashlight`允许旧绑定临时关闭；finalizer在正常和异常路径都释放许可。新灯绑定回调只安排下一次安全Update重应用原生灯状态，不能在回调里立刻递归调用Receive，因为Receive又可能进入PrepareHelmetFlashlight。0.5秒维护用于初始化和恢复，稳定时不重复发送开灯网络请求。装备交接实机行为仍是未测项。

### 为何之前“强制常亮”仍会熄灭

原生`RootPlayerBotAction.Update`内联了灯光判断，直接调用IsFlashlightAllowed和Sync入口，没有调用独立的UpdateFlashlightState。旧补丁只拦辅助函数，真实内联路径仍可关闭背包开关。

原版还有1.5秒关灯后冷却；旧0.5秒轮询重新开灯时，内联判断可能再次关灯并刷新关灯时间，形成循环。把原生开灯判断放宽、提高强度或延长一次开灯，都不能覆盖这个写入漏洞。0.5.14在真正写入边界拒绝false，才补上此路径。

当前GameAssembly静态核验的原版规则：Exploration／Encounter／Combat／Survival进入后续判断，其他默认阶段可能拒绝；附近合格休眠敌人、前方真人和冷却均影响原版决策。原版静态默认的休眠敌人距离25米、真人距离15米且方向点积>0.9，另有图节点和休眠状态过滤。这些是当前原始游戏静态默认，不代表任何MOD组合的运行时参数。首次关灯具体来自哪条AI分支，旧日志没有独立证明。

本轮常亮通过不等于“照到敌人一定不会惊醒敌人”；敌人反应应另行验收。

## 副相机、原生灯和雾气如何协作

副相机渲染现有场景灯。背包开关开启、源参数有效和实际照出像素是三个环节，不能相互代替。

`NativeBotLamp`检查源灯身份、有效参数、原生聚光灯数据、阴影分配和可见灯集合。只有原生渲染状态就绪才隐藏已有RF替代层；下一帧失效就归还原层显隐。`TempDisableLight`只作观察，不能仅凭allocated=false就认定阴影资源耗尽，更不能把它与Wants／FlashlightEnabled=false混同。

`BotLightViewScope`在副相机拍摄期间临时借用既有原生灯的FPS角色与强制阴影引用，使用原生IsFPSPlayerLight属性同步相关状态；必要时临时SetOn重试。拍摄finally中恢复本体与目标的角色、强制位、原阴影引用、shader索引和借用的渲染开关，再让本体重新裁剪。这不是额外生成一盏观测灯。

副相机使用独立渲染器和雾资源；减雾桥只登记自己的相机，沿用FlashlightCustom已有开关和倍率，结束时恢复拍摄前实时Shader状态，不把本体重新写回未经减雾的原始FogSettings。不修改任务雾或感染规则。

## 过曝问题的实际原因与保留修复

“过曝”是故障现象，没有应该保留的“过曝功能”。旧日志和测试排除了把Q退出白亮简单归为缓存或一次手电请求的解释：关闭额外灯、禁用插件元数据缓存后仍发生；实际安装哈希已核对。

确认的关键缺陷是副相机污染了共享渲染状态：原生PreLitVolume会全局绑定体积／雾纹理，而旧恢复只顾部分数值或灯缓冲；关闭窗口释放副相机资源后，本体仍可能引用这些纹理。按T重新初始化可暂时恢复，符合该故障路径。

当前必须保留以下代码：

1. `FogShaderState`保存并恢复六个全局纹理：`_LitVolume`、`_FogVolume`、`_DensityNoise`、`_IndirectVolume`、`_ReflectionVolume`、`_LitBufferCopy`，以及对应尺寸、峰值／色调等原值。
2. `LightBufferBindings`恢复七个共享灯／雾缓冲绑定。
3. `NativeCapture.Capture`的finally归还灯角色、减雾作用域和RenderGlobals；失败同样执行收尾。
4. `NativeCapture.Dispose`先恢复本体全局绑定，再释放副相机自己的GPU资源；自有雾组件按身份清理，不能顺手清空本体的全局雾球。

不是删掉所有Shader写入就安全：这些恢复写入正是退出过曝的修复。新功能若借用全局状态，必须在同一作用域保存和恢复真实引用；仅把亮度数值改回去不够。

### 当前源码和已安装DLL中还保留了什么

此次对两个已安装DLL进行了Cecil只读检查，结合源码与原构建输入核对：

| 内容 | 当前状态 | 后续处理 |
| --- | --- | --- |
| 旧独立观测灯`ObservationLight` | 两个安装DLL中不存在此类型，没有新增Unity Light或CL_ShadowGenerator的直接创建调用 | 不重新引入为常亮补丁 |
| 接管专用灯／额外阴影工厂方案 | 当前沿用既有原生灯；没有上述独立创建路径 | 不与必要的原生FPS灯作用域混同 |
| NativeFlashlight手动UpdateData／UpdateTransform／UpdateTransformData | 没有这些主动调用；UpdateData前缀仍用于拒绝无效参数 | 保留校验，不恢复手动GPU刷新 |
| 直接强制Unity Light.enabled或写灯参数 | 两个安装DLL中没有Unity Light属性setter直接调用；当前参数修正发生在原生写入前缀的输入保护中 | 不绕过原生裁剪／同步 |

## 后续验证顺序

1. 核对加载版本／文件哈希和AllBots配置，再看暗处墙地面的真实光斑；不以F提示或模型发光替代照明。
2. 先测无T观察，再测T观察／接管、Q退出驻守及再次接管；最后离关重进，检查本体曝光与雾。
3. **待补测**：能让人机切换装备后，验证主副武器、近战与工具绑定后的恢复，以及解绑异常不会遗留关灯许可。没有此操作入口时如实保留未测，不为填测试表顺带新增指令。
4. 若仍熄灯，关联`[人机恒亮拒绝关灯]`、`[原生灯渲染状态]`和`[副相机原生手电]`：wants／enabled反复false优先查漏写入口，开关true但无像素再查源灯、可见性、数据和阴影。
5. 若Q退出后本体白亮，优先检查全局纹理／缓冲和释放顺序。不能把“没有额外灯”当作共享渲染状态已安全，也不要未经哈希与日志核对就再次归因缓存。
